# v0.12.0 - Screenshots that know where their words are

**2026-11-21**

## TL;DR

`screenshot_page` and `screenshot_by_uid` take a new option, `textBoxes: true`. Alongside
the picture you get every visible line of text on it, read from the page itself, with its
box in the pixels of the image you received:

```
{"width":1000,"height":700,"boxes":[
{"text":"Example Domain","x":300,"y":198,"w":60,"h":24},
...
]}
```

Inline, that JSON is its own text block. With `saveTo`, it is written next to the image as
`<image path>.boxes.json`. Nothing changes for calls that do not ask for it.

## Why

Agents annotate screenshots: circle the button, underline the error, point an arrow at the
number that matters. To do that they need to know where the words sit in the picture. Until
now they guessed from the pixels, or ran OCR on an image whose text the browser already
knew exactly.

The browser knows. Every word on the page has a measured rectangle; the work is turning
that into the coordinates of one particular picture, which may be a device-pixel capture at
twice the CSS size, a clip of the document, one element, or a copy the server shrank to
save tokens.

## Highlights

| What | Detail |
|---|---|
| One line per box | Words merge into a line when they share a line, a block and a small gap. Nav links stay separate. |
| Image pixels, always | CSS px times `devicePixelRatio`, minus the region origin, clamped to the image. When the inline image is downscaled the boxes are rescaled with it. |
| Only what you can see | Hidden by `visibility`, `display` or `opacity`, outside the region, clipped by an overflow ancestor, or covered by another element: left out. |
| Every capture mode | Viewport, `fullPage`, `clip`, `selector`, and element captures by uid or selector. |
| Sidecar file | With `saveTo`, `<image path>.boxes.json` beside the full-resolution image, swept with it. |
| Never costs the picture | If measuring fails, the screenshot comes back with a note. |

## How it works

One BiDi call runs a measuring function in the page. It walks text nodes (open shadow
roots too), makes a Range per word and reads its client rectangles, then drops words that
fail `checkVisibility`, fall outside the captured region or an ancestor's overflow clip, or
sit under an unrelated element at their centre (`elementFromPoint`). Words are merged into
lines in DOM order. The page returns CSS pixels and its `devicePixelRatio`; the server
converts to image pixels and clamps to the size read from the image header.

Inline images are shrunk later, at the response boundary, by `shrinkImageBlocks`. That step
now also finds the text-boxes block whose size matches the image it shrank and rescales the
boxes, so `width` and `height` always equal the image you got.

Not covered: form field values, `::before`/`::after` content, text inside iframes. Caps:
30000 words scanned, 1000 boxes inline, 10000 in a sidecar, with a note when cut.

## Getting the sidecar when your client saves the reply

If your client saves tool results to disk itself (so the server never sees the path), the
inline reply is what arrives. The boxes are the one text block whose text starts with
`{"width":`; write that text unchanged to `<your image path>.boxes.json`.

## Config

None.

## Upgrading

Nothing to do. The option is off by default and the reply is unchanged without it.
