# v0.11.0 — The whole page, the picture on it, and no files left behind

**2026-11-11**

## TL;DR

`screenshot_page` could only photograph the viewport, as PNG. It now captures the whole
document, a box, or one element, as PNG or JPEG, and tells you where Firefox had to cut a
page too long for one picture. A new read-only tool, `extract_images`, lists the images on
a page and hands back the ones you pick as real image blocks: the page's own bytes when it
can get them, a photograph of the element when it cannot, and a label saying which.

**Behaviour change:** `saveTo` no longer writes where you tell it. It writes a copy into
the server's own folder, inside its container, and deletes it after `MCP_ASSET_TTL_MIN`
minutes. If you relied on `saveTo` putting a file at a path of your choosing, that file is
no longer there; take the image block from the reply instead.

## Why

Agents use this server to capture pages as proof, or as figures for a document. Three
things got in their way.

**The viewport was the only picture.** A long article, a full dashboard, a single chart:
each needed a scroll-and-stitch loop or a guess at where the interesting part was.
Firefox's own capture has always been able to do the whole document, a box or an element;
the server just never asked it to.

**Getting the image on a page meant writing code.** To pull out an `<img>`, an inline
mermaid `<svg>` or a `<canvas>`, agents wrote their own `evaluate_script` that fetched or
rasterised it, and got back a data URL buried in JSON that they then had to decode. Every
agent wrote it slightly differently, and none of them handled the cross-origin case.

**`saveTo` wrote files nobody could read, and nobody deleted.** Callers passed paths from
their own machine. The server is in a container on another machine, so the file landed in
the container, where the caller could never reach it, and stayed there. Production had
quietly collected dozens of screenshots in its writable layer. The asset janitor skipped
caller paths on purpose, so nothing would ever have removed them.

The rule all three changes follow: **the server returns images as image blocks; getting a
file onto your disk is your client's job.** Files the server writes are its own
short-lived copies, and they are swept.

## Highlights

| Change | Effect |
|---|---|
| `screenshot_page` gains `fullPage`, `clip`, `selector` | the whole document, a box in document CSS pixels, or the first element matching a CSS selector; at most one per call |
| `format: 'jpeg'` and `quality` on both screenshot tools | much smaller pictures of photos and long pages; the image block's mime type follows |
| `screenshot_by_uid` accepts `selector` | name an element by CSS instead of taking a snapshot first; exactly one of `uid` or `selector` |
| Long pages are cut with a note, never silently | past 32,767 device pixels the reply gives the real height, where it stopped, and the `clip` that gets the rest |
| New tool `extract_images` | list mode returns a numbered text list; pick mode returns up to 10 images, each labelled `original` or `rendered` |
| Tall pictures fit their width | a full page more than twice as tall as wide is shrunk to a readable width instead of a ~130 px sliver |
| No side over 8000 px | the model API rejects larger images and takes the whole reply down with them |
| JPEG is downscaled too | previously only PNG was shrunk; a JPEG went out at full size |
| `saveTo` copies are swept | written to `~/.firefox-devtools-mcp/screenshots/`, deleted after `MCP_ASSET_TTL_MIN` minutes |

## How it works

**Regions are passed straight to Firefox.** The capture call now takes an origin, a clip
and a format instead of hard-coding the viewport. A selector is resolved with BiDi
`browsingContext.locateNodes` and captured as an element clip; if it matches more than one
element, the first is captured and the reply says so. The plain viewport PNG is exactly
the request it always was.

**New options are BiDi or nothing.** The old fallback for a lost BiDi channel is the
WebDriver classic capture, which can only photograph the focused tab's viewport. For a
full-page or element request that would be a different picture returned as if it were the
right one, so these options fail with a text error instead. They capture the tab by its
BiDi context, so it is never raised and the person's view does not move.

**The cut is measured, not discovered.** Before a full-page capture the server reads the
document's scroll size and device pixel ratio, and clamps the box to Firefox's per-side
and per-area limits, both in device pixels. On a 40,000 px page at ratio 1 you get the
first 32,767 px and a sentence telling you to ask for `clip` with `y: 32767` for the rest.
`clip` boxes get the same clamp.

**`extract_images` reads, then falls back to looking.** One `script.callFunction`
enumerates images in document order, and pick mode re-runs the same enumeration so an
index means the same image if the page has not changed. An `<img>` or CSS background is
fetched from its URL; PNG and JPEG go out as they are, anything else (GIF, WebP, AVIF,
SVG) is redrawn to PNG. Inline SVG is serialised and rasterised at `scale` over white; a
canvas is read directly. When any of that fails, typically a cross-origin image without
CORS or a tainted canvas, the element is photographed and the line says `source:
rendered`. Nothing is written into the page and nothing goes through the privileged
browser context: the person may be using that tab. Each picked line repeats `src=`, so you
can check you got the image you meant.

**Downscaling learned two shapes and one format.** `jpeg-js`, pure JavaScript with no
native build, decodes and re-encodes JPEG blocks at quality 85 through the same area
average as PNG. A block more than twice as tall as wide fits its width to the budget;
everything else keeps the long-edge rule, so viewport screenshots and the pictures
attached to mutations come out exactly as before. Any failure still returns the original
bytes.

**`saveTo` keeps its name and type, so no call breaks.** The base name of whatever you pass
is kept, stripped to safe characters, prefixed with a timestamp, and given the extension of
`format`. The reply gives the real path, its size, and how long it lives, and says so when
your path was not used. The janitor now sweeps that folder alongside recordings and
browser logs. Files written to other paths by earlier versions are not migrated; the next
container recreate removes them.

## Config

| setting | effect |
|---|---|
| `MCP_ASSET_TTL_MIN` | minutes a written file survives, now including `saveTo` copies. Default 60, production compose sets 60; 0 turns cleanup off |
| `detail` per call, `--screenshot-max-edge`, `--screenshot-auto-max-edge` | unchanged; `extract_images` uses the same budget as the screenshot tools |

New dependency: `jpeg-js`. No new flags.

## Upgrading

Rebuild the production image: `cd docker && docker compose build mcp && docker compose up
-d --no-deps mcp`. `--no-deps` keeps the browser and the person's tabs alive. Confirm with
`docker exec firefox-mcp npm ls -g --depth=0`. The recreate also clears any files that
older versions wrote to caller paths inside the container.

If anything of yours reads files that `saveTo` wrote, change it to use the image block in
the reply. The server's copy is inside its container and lives for an hour at most.
